## 一、整体架构概览

```
                        ┌──────────────────┐
                        │     Web 管理端     │
                        │  (web/index.html) │
                        └────────┬─────────┘

┌─────────────────────────────────────────────────────┐

│  /api/client/heartbeat     ← 心跳 + 任务分发         │
│  /api/client/task_report   ← 进度/状态上报           │
│  /api/client/task_result   ← 最终结果上报            │
│  /api/v1/tasks/*           ← Web 端 REST API         │
│  /api/v1/clients           ← 在线客户端查询          │
│  /api/v1/items             ← 采集结果查询            │
└──────────────┬─────────────────────────┬────────────┘
               │                         │
       ┌───────▼────────┐       ┌───────▼────────┐
       │  Client-001     │       │  Client-002     │
       │  platform: 1688 │       │  platform: 1688 │
       │  capability:    │       │  capability:    │
       │    image        │       │    price        │
       │  逐页逐商品爬取  │       │  插件导出Excel  │
       └────────────────┘       └────────────────┘
```

### 核心交互流程

```
1. 客户端启动 → 循环发送心跳 (每5秒)
2. 心跳响应 → start_crawl / none
3. 收到任务 → 参数校验 → accept_task → 执行爬虫
4. 爬虫执行中 → report_progress 上报进度
5. 爬虫完成 → report_result 上报商品数据
6. 任务被取消 → 心跳返回 stop_crawl → stop_task → 爬虫退出
```

## 二、严重问题

### 2.1 任务状态被 report_progress 错误覆盖

**位置**：`client/task_manager.py#L58` 和 `server/app/routes/client.py#L118-L144`

**问题**：
```
start_task() 调用链:
  report_progress(task_id, "running", ...)    → 服务端 status="running"  ✅
  accept_task(task_id)                        → 服务端 status="accepted" ❌ 覆盖了 running
```

`accept_task()` 内部调用 `report_progress`，传入 `status="accepted"`，服务端 `task_report` 直接将其写入数据库的 `status` 字段，导致任务状态被改为 `accepted`。

**实际效果**：任务创建后状态流转变为 `pending → running → accepted → running`，中间出现一个短暂的 `accepted` 状态，如果 Web 端恰好此时查询，会看到异常的 `accepted` 状态。

**影响**：`accepted` 状态在 Web 端没有对应的 CSS 样式和筛选项，会显示为无样式文本。

---

### 2.2 取消任务时 current_task_id 未被清空

**位置**：`client/task_manager.py#L103-L108`（两个客户端都有）

```python
def stop_task(self):
    print("[任务管理] 收到停止指令")
    if self.current_task_id:
        self.api.report_progress(self.current_task_id, "canceled", ...)
    self._stop_event.set()
    self.running = False
    # ❌ 缺少: self.current_task_id = None
```

**问题**：`stop_task()` 设置 `running = False` 但**没有清空 `current_task_id`**。

**影响**：
1. 下次心跳时仍会上报这个 `current_task_id`
2. 服务端检查取消逻辑（第64-76行）会再次匹配到 `status="canceled"` 的任务，反复返回 `stop_crawl` 指令
3. 客户端进入"反复收到 stop_crawl → 反复上报 canceled"的死循环

### 2.3 验证码等待期间无法响应任务取消

**位置**：`client/main.py#L128-L174`

```python
while "验证码" in tab_detail.title and wait_count < max_wait:
    time.sleep(1)       # 只会 sleep，不检查取消状态
    wait_count += 1
```

**问题**：验证码等待循环中没有调用 `check_task_canceled()`。如果服务端在验证码等待期间取消了任务，客户端要等到 5 分钟超时后才知道。

**影响**：验证码等待期间取消任务无效，用户体验差。

---

### 2.4 client/main.py 异常处理缩进错误

**位置**：`client/main.py#L258-L296`

```python
    except Exception as e:
        print(f"价格解析异常: {e}")
                                       # ← 空行
        print('未找到价格')             # ← 缩进在 except 块外！实际属于 try 块
```

四个 `except` 块都存在这个问题：
- `价格解析异常` (L258-L272)
- `供应商解析异常` (L274-L286)  
- `描述解析异常` (L288-L296)

**问题**：`except` 块内的 `print('未找到价格')` 等语句由于前面有空行且缩进不规范，**实际不在 except 块内**，而是回到了 `try` 块的作用域。这导致异常处理块是空的。

**影响**：如果解析异常被捕获，`except` 块什么都不做就继续执行，变量保持空字符串但不会报错，属于潜在隐患。

### 2.5 服务端 task_result 硬编码 platform

**位置**：`server/app/routes/client.py#L199`

```python
item = {
    ...
    "platform": "1688",       # ❌ 硬编码，无论任务实际是什么平台
    ...
}
```

**问题**：`client/main.py` 的 `shop_detail()` 返回的 `product` 字典里**没有 `platform` 字段**，服务端也不从任务对象读取平台信息，直接硬编码 `"1688"`。

**影响**：虽然目前只有 1688 平台，但架构上已经支持多平台（京东、拼多多），此处硬编码导致未来扩展时会出错。

## 三、中等问题




### 3.2 report_progress 和 report_result 无返回值/无状态检查

**位置**：`client/api_client.py#L81-L113`

```python
def report_progress(self, ...):    # 返回 None
def report_result(self, ...):       # 返回 None
def accept_task(self, ...) -> bool: # 有返回值但调用方未检查
```

**问题**：
1. `report_progress` 上报失败静默忽略，客户端不自知
2. `report_result` 同理，如果网络故障结果可能丢失
3. `accept_task` 的返回值在主流程中未检查就继续执行爬虫

**影响**：状态上报不可靠，失败时无重试机制，存在数据丢失风险。

---

### 3.3 服务端 task_report 无条件覆盖 status

**位置**：`server/app/routes/client.py#L120-L122`

```python
update_data = {
    "status": status,       # ← 直接覆盖，不管之前是什么状态
    ...
}
```

**问题**：不管客户端上报什么状态，服务端都会直接覆盖数据库中的 `status` 字段。例如：
- 任务已 `running`，客户端上报 `accepted` → 数据库变为 `accepted`
- 任务已 `canceled`，客户端延迟上报 `running` → 数据库变为 `running`（取消失效）

**建议**：增加状态转移校验，只允许合法的状态转移。

---

### 3.4 report_result 没有去重保护

**位置**：`server/app/routes/client.py#L173-L233`

**问题**：同一个 `task_id` 如果被多次调用 `report_result`，会导致商品数据重复插入 `collector_items` 集合。

**建议**：插入前检查 `taskId` 是否已有结果，或使用 `dedupeKey` 的 upsert 操作。

## 四、轻微问题

### 4.1 Web 端统计只基于前100条数据

**位置**：`web/index.html` `loadStats()` 函数

```javascript
const tasksData = await apiRequest(`${API_BASE}/tasks?page=1&pageSize=100`);
```

**问题**：统计数据只基于前 100 条任务，如果数据库中有超过 100 个不同状态的任务，统计数据不准确。

**建议**：新增一个专门的统计接口 `/tasks/stats`，返回各状态的计数。

## 五、状态转移图（当前实际 vs 预期）

### 当前实际状态转移

```
                    ┌──────────┐
                    │ pending  │
                    └────┬─────┘
                         │ get_pending_collector_task (变为 running)
                         ▼
                    ┌──────────┐
                    │ running  │ ← accept_task 又上报 accepted 覆盖这里
                    └────┬─────┘
              ┌──────────┼──────────┐
              ▼          ▼          ▼
         succeeded   failed    canceled
         
    running 状态下还可能被 report_progress 覆盖为:
    - accepted (accept_task 上报)
    - waiting_captcha (虽未作为独立 status 字段保存，但 progress.status 有此值)
```

### 预期状态转移

```
                    ┌──────────┐
                    │ pending  │
                    └────┬─────┘
                         │ 心跳分配 (原子操作)
                         ▼
                    ┌──────────┐
                    │ running  │
                    └────┬─────┘
              ┌──────┬────┼──────┬──────┐
              ▼      ▼    ▼      ▼      ▼
         succeeded  failed  │  canceled  paused (可选)
                            │
                     waiting_captcha
                         (子状态,仍算 running)
```
